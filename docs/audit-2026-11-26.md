# Audit of 2026-11-26

A snapshot. [progress.md](progress.md) is the living record and says what
is being done about each item; this file is the evidence it was drawn from.

## Method and limits

* Audited commit: `63bcca4`. Five scopes: the GPU layer, the shader
  translator, runtime and formats, and two research tracks over the
  reference repositories (GPU and shaders; assets and rendering).
* Each scope was read by one auditor and then by a second reader whose job
  was to refute the first against the cited code. 98 claims were checked:
  72 confirmed, 25 corrected in part, 1 unverifiable, none refuted
  outright. Statements below are the corrected ones.
* **Nothing was built against a title or run.** No game data was present.
  Every statement about where a frame's time or the memory goes is a
  mechanism read in the code, not a measurement, and is marked so.
* The auditors worked from the README's figures for another machine. Where
  they concluded that the target machine cannot do something, that
  conclusion is not carried over: the owner reports the title running at
  about 15 fps on it. Memory and speed are settled by profiles
  (progress.md, "Measuring").
* No content-derived fingerprints of shipped data appear here.

## Gate: where the title's files come from

Open, and the owner's to answer. Recorded as facts.

* The reference repositories describe the only data of this build they
  know as "the circulating package" (`gta6-pc-port-hub` README and package
  inventory) and "the leaked package" (`xbox-hle-lab` posting policy and
  contribution rules). The hub records that this package holds no
  executable and that for this reason nothing boots in any project.
* VIctory identifies one executable, of a build it labels with the same
  version, "from a local package" (`crates/victory-game/src/lib.rs`), and
  its README reports the title booting to the prologue. It reads the
  executable as a plain file and needs every other file readable beside
  it. No repository says how such files are lawfully produced.
* VIctory itself contains no decryption, key handling or package-container
  code (searched twice, independently). The title's own code reads its own
  archives.
* What the runtime answers the title: the game licence is always active,
  not a trial, without expiry; a package licence is valid for the title's
  own identifier; the package reports as installed; one offline local user;
  the network is loopback only. No check of ownership exists. The loader
  runs a prepared copy of the executable (import directory and entry point
  neutralised, integrity flag cleared).

The project's standing rules require lawfully obtained data and no bypass
of access controls. Until the owner says where the files used for runs
come from and how they became readable, sessions work on VIctory's own
code, synthetic data and checks that need no title files.

## Memory

All mechanisms; no sums. The README's 33 GB is commit on another machine,
which a paging file satisfies; what 16 GB of RAM does to frame time is
unmeasured.

| ID | Finding | Evidence |
|---|---|---|
| A-M1 | Title memory is allocated as the title asks (the console's 10 GiB + 3.5 GiB in Series X mode); nothing accounts or enforces the console's budget | code |
| A-M2 | Each title buffer a draw uses gets a whole-buffer committed host copy in system memory. Their sum is recorded nowhere | code |
| A-M3 | Fixed costs: a 512 MB snapshot pool; 4 MiB loose windows never freed; per view heap an 8 MB stride table, a 16 MB mark table and a 16.8 MB page table; a 64 MB staging pool; the pipeline library blob | code |

measured, and the README's 1 s frame is another machine's. Not worked
before the correctness track, and never at its cost.

| ID | Hypothesis | Evidence | How a run settles it |
|---|---|---|---|
| A-P1 | Submissions are prepared, run, waited for without limit and copied back one at a time under two process-wide locks; CPU and GPU never overlap (the file header calls it a shortcut) | code | `preparing_ms` + `gpu_ms` against the frame time; submissions a frame |
| A-P2 | GPU time inside the waited submissions: host copies of title buffers and three per-heap lookup tables live in system memory and are read by shaders across the bus; a clamp dispatch and two global barriers per indirect call; whole depth-twin copies | code | `gpu_ms`; `VICTORY_GPU_TIMING`. | A-P3 | Translated loops run to the 2^20 limit where they read data with no host copy | code; the README offers it | the loop-limit switch re-translates every shader and remakes every pipeline first: a long run, not a quick A/B |
| A-P4 | Read and write marks add an unordered-access load and a conditional atomic to pixel shaders that read heap textures, with no forced early depth test, which by Direct3D's rules disables early depth rejection for them | code; consequence inferred | a build with marks off for comparison, picture checked against captures |
| A-P5 | Title-thread stalls the frame line does not show: page-guard faults under one lock, a 500 ms a frame pipeline wait, the heap and buffer locks | code | frame time minus (`preparing_ms` + `gpu_ms` + copying back) |

## What the audit corrected in the project's own documents

* The README says one machine was tested. Code comments record
  observations on an RTX 4050 Laptop, an RX 9070 XT, an RTX 5090D and
  NVIDIA-specific behaviour, so NVIDIA paths have been exercised; no world
  run on NVIDIA is recorded.
* The README's 4 MB pipeline library is the AMD figure.
* "No pacing" would be wrong: `frame.rs` ticks at the title's frame
  interval and the title waits on it. It is not tied to the display.
* The `pipeline.rs` and query module headers are stale against the code.
* VIctory's count of 24,387 programs has no stated method; other projects'
  26,503, 25,471 and 21,522 count different things (database records,
  graphics pipelines, code blobs).
